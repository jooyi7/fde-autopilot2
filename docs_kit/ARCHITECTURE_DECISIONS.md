# 📋 프로젝트 설계 판단 및 검증 보고서 (ARCHITECTURE_DECISIONS.md)

## 1. 문제 정의 및 아키텍처 핵심 원칙
- **핵심 해결 과제:** 입력 데이터의 정합성을 보장하고, 일관된 비즈니스 판정 기준과 신속한 의사결정 리포트를 제공하는 시스템 구축.
- **설계 철학 (80/20 분리 아키텍처):**
  - **결정론적 코어 엔진 (80%):** 수치 연산, 임계치 비교, 상태 전이 등 정확성이 생명인 로직은 순수 함수 기반의 결정론적 모듈로 구현하여 환각(Hallucination) 가능성을 원천 차단함.
  - **유연한 AI 어드바이저 (20%):** 결정론 코어가 확정한 구조화된 판정 결과를 바탕으로 조치 가이드 및 요약 브리핑만 생성하도록 역할을 명확히 분리함.

## 2. 주요 설계 판단과 근거 (Design Decisions & Rationale)
1. **데이터 파싱 및 결측치(Anomaly) 방어 설계**
   - **판단:** 원본 데이터를 직접 수정하지 않고, 파서 계층에서 결측치(`null`, `NaN`, 빈 문자열, 센티널 값)를 사전 필터링 및 별도 플래그(`INVALID_DATA`)로 분리함.
   - **근거:** (실무자 에이전트 DM 확인 결과 및 데이터 스캔 결과 반영) 오염된 데이터가 전체 평균이나 핵심 통계를 왜곡하는 것을 방지하고 데이터 감사 추적성(Traceability)을 확보하기 위함.
2. **문서(README)와 실무자 에이전트(DM) 요구사항 상충 시 우선순위 원칙**
   - **판단:** 초기 문서(`README.md`)의 모호한 표현이나 상충되는 조건이 발견될 경우, 실무자 에이전트(업무 담당자 DM)를 통해 확정한 현업 기준을 최종 Ground Truth로 채택하고 설정(`CONFIG`)에 명시함.
   - **근거:** 실제 비즈니스 의사결정 기준과의 정합성을 맞추고 협업 과정을 투명하게 문서화하기 위함.
3. **설정 분리형 임계치 관리 (Maintainability)**
   - **판단:** 판정 기준값(임계치, 가중치, 상태 규칙 등)을 비즈니스 로직 내부에 하드코딩하지 않고 상단 설정 객체(`CONFIG`)로 외재화함.
   - **근거:** 향후 운영 조건이나 사내 규정이 변경될 때 개발자가 아닌 실무 담당자도 설정값만 수정하여 즉시 대응할 수 있도록 유지보수성을 극대화함.
4. **무중단 Fallback 메커니즘 (Resilience)**
   - **판단:** AI API 지연이나 일시적 오류 발생 시에도 시스템이 중단되지 않고, 코어 엔진의 수치 판정 결과와 표준 템플릿 기반의 브리핑을 즉시 반환하도록 구현함.
   - **근거:** 현업 모니터링 및 판정 업무는 외부 AI 네트워크 상태와 무관하게 무중단으로 동작해야 하기 때문임.

## 3. 검증 결과 (Verification & Testing)
- **단위 및 경계값 검증:** 정상 케이스뿐만 아니라 임계치 경계값(Boundary), 결측 데이터, 빈 배열 입력에 대한 결정론 코어 단위 테스트 통과.
- **엔드투엔드(E2E) 화면 검증:** 플랫폼 내장 Browser(`0.0.0.0` 바인딩 및 실제 포트 연결) 환경에서 필터링, 상세 조회, 상태 변경 및 예외 처리 동작을 직접 클릭하여 확인 완료.

## 4. 남은 한계점 및 향후 개선 방향 (Limitations & Future Work)
1. **대용량 실시간 스트리밍 처리:** 현재는 배치/파일 단위의 인메모리 파싱 구조로 동작하므로, 수백만 건 이상의 실시간 데이터 유입 시에는 서버사이드 페이지네이션 및 데이터베이스 인덱싱 연동이 필요함.
2. **권한별 세분화된 접근 제어(RBAC):** 현업 배포 시 일반 사용자와 관리자의 임계치/규칙 수정 권한을 분리하는 인증 계층 추가가 요구됨.
3. **AI 브리핑 피드백 루프:** 실무 담당자가 AI가 제안한 조치 가이드의 정확도를 평가(채택/수정)하고 이를 프롬프트 컨텍스트에 반영하는 피드백 파이프라인 확장 가능.
